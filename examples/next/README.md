# Next.js example

App Router, one Client Component owning the instance — and a real `next build` to prove the
integration survives server rendering, the client boundary and TypeScript.

```sh
npm install                  # next, react, react-dom, typescript and the library (file:../..)
npm run build                # next build — includes the TypeScript check
npm run start                # next start, then open the printed URL
```

This example is a **separate package with its own dependencies on purpose**. Next pulls in a large
tree, and none of it belongs in the library's own install surface: `npm install visual-region` must
not bring a framework with it. The repository's own check script installs and builds this directory
only when it is asked to.

What it demonstrates:

- `app/page.tsx` is a **server component** with no client state; `app/RegionDemo.tsx` starts with
  `'use client'` and owns everything that touches the library;
- the instance is created in `useEffect`, on the node held by a ref — after hydration, never during
  the server render, where there is no DOM;
- cleanup on unmount releases every subscription and calls `destroy()`;
- `setRegion(bounds)` / `clearRegion()` from click handlers, with the rect measured from the node;
- the `start` / `change` / `end` / `unsupported` events driving React state.

The check that runs in this repository proves more than "it builds": after `next build` it also
verifies that the library code is present in the **client** chunks (not only in the server ones),
starts the production server and runs the same browser battery as the other examples — the region is
opened by a real pointer drag and the pixels are compared before/after.

`next-env.d.ts` and `.next/` are generated by Next and are not committed.
